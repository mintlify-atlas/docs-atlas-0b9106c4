EVerest is an open-source, modular firmware stack for electric vehicle (EV) charging stations, hosted under [Linux Foundation Energy](https://lfenergy.org/). By digitally abstracting the complexity of multiple charging standards and hardware platforms, EVerest runs on everything from simple unmanaged AC home chargers to complex multi-EVSE public DC charging stations with battery storage and solar integration. Its goal is to ensure every car works with every charger and every charging network — interoperably and securely — by translating charging standards into well-tested, production-ready code.

## Why EVerest

The EV charging ecosystem is fragmented: dozens of hardware vendors, multiple evolving protocols, and strict certification requirements make building a reliable charger software stack difficult. EVerest solves this by providing a shared, community-maintained base layer that handles the hardest parts — protocol stacks, hardware abstraction, energy management, and security — so that manufacturers and integrators can focus on their differentiated features instead of reinventing foundations. The project was initiated by PIONIX GmbH and is now an active open-source community under the Apache 2.0 license.

## Architecture Overview

EVerest is built around a **microservice-like module architecture**. Each functional unit — a charging port controller, a protocol stack, a hardware driver, an authentication handler — runs as an independent operating system process. All inter-module communication flows through a central **MQTT broker**, keeping modules loosely coupled and independently replaceable.

The **Manager** process is the orchestrator: it reads a YAML configuration file, resolves module dependency graphs, spawns each module as a child process, and supervises the system lifetime. Modules declare their capabilities and requirements in a `manifest.yaml` file. The framework validates connections at startup and routes MQTT messages according to the declared interface topology.

Modules can be written in **C++**, **Python**, or **Rust**. The `ev-cli` developer tool generates implementation stubs from manifest and interface definitions, so adding a new module or hardware driver requires writing only the business logic.

```text
┌─────────────────────────────────────────────────────┐
│                   EVerest Manager                   │
│        (reads config, spawns & supervises)          │
└────────┬────────────────────────────────┬───────────┘
         │  MQTT broker (mosquitto)        │
   ┌─────▼──────┐  ┌──────────────┐  ┌───▼──────────┐
   │ EvseManager│  │  OCPP 2.0.1  │  │  YetiSimulator│
   │  (module)  │  │   (module)   │  │   (module)    │
   └────────────┘  └──────────────┘  └───────────────┘
```

Each module publishes **VARs** (variables) and exposes **CMDs** (commands) over MQTT. Connected modules subscribe to VARs they need and call CMDs they require, as declared in their manifests. This design allows modules to be swapped at configuration time without recompiling the rest of the stack.

## Hardware Requirements

EVerest can run on any Linux-based operating system that provides the required dependencies. Yocto is the strongly recommended platform for production deployments. The resource footprint scales with the number of active modules; the table below shows the general minimums.

| Resource | Minimum | Recommended |
|----------|---------|-------------|
| CPU | imx6ULL or comparable | imx93 or AM62x |
| RAM | 512 MB | 1 GB or more |
| Flash | 1 GB | 4 GB or more |

For development and simulation work, EVerest runs comfortably on any modern x86-64 Linux workstation or inside a dev container on macOS or Windows via Docker.
