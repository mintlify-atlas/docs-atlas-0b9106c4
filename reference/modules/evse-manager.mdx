The `EvseManager` module is the central charging kernel in EVerest — one instance manages exactly one EVSE (Electric Vehicle Supply Equipment). It orchestrates the full IEC 61851 control pilot state machine, coordinates High-Level Communication (HLC) via ISO 15118 and SLAC, collects session energy data, and exposes the EVSE as a node in EVerest's energy management tree. Protocol modules such as OCPP and API layers always interact with EVSEs through the `evse_manager` interface that EvseManager provides.

## What EvseManager Does

EvseManager handles every aspect of a charging session from the moment a connector is plugged in to the moment it is unplugged:

- **IEC 61851 state machine** — drives Control Pilot states A through F (and the error state F) in software; the lowest-level PWM generation and pilot reading are delegated to a Board Support Package (BSP) module.
- **High-Level Communication** — optionally coordinates SLAC (signal level attenuation characterization) and the ISO 15118-2/DIN SPEC 70121 stack for plug-and-charge, smart-charging, and DC cable check sequences.
- **Session lifecycle events** — publishes `session_event` variables for every significant transition (plug-in, authorization, charging start/stop, error, unplug) so that OCPP, display, and API modules can react without polling.
- **Energy management node** — acts as a leaf node in the EVerest energy tree; it publishes energy flow requests up the tree and receives enforced current/power limits back from the EnergyManager.
- **Autocharge / Plug & Charge token provider** — optionally provisions RFID-equivalent authorization tokens derived from the SLAC MAC address or the ISO 15118 EVCCID, feeding the Auth module.
- **Powermeter aggregation** — republishes the power meter reading from whichever meter is used for billing (DC-side meter takes priority over AC-side in DC applications).

## IEC 61851 State Machine

EvseManager implements the full IEC 61851-1 control-pilot state machine. State transitions are triggered by BSP events (pilot voltage measurement, proximity pilot) and by commands from OCPP or the Auth module.

<Tabs>
  <Tab title="AC Basic Charging">

    In basic AC mode, the state machine follows the standard IEC 61851-1 sequence:

    ```text
    A (no vehicle) → B1 (vehicle detected, no PWM) → B2 (PWM active)
         → C2 (charging, PWM) → B1 (charge pause or unplug) → A
    ```

    - **State A**: No vehicle connected; pilot at +12 V, no PWM.
    - **State B**: Vehicle connected; pilot at +9 V. EvseManager starts PWM to signal available current.
    - **State C**: Vehicle switches on; charging current flows.
    - **State D**: Ventilated charging — only allowed when `has_ventilation` is `true`.
    - **State E/F**: Error states; F is used to signal faults and during reinitialization.

    The `state_F_after_fault_ms` parameter controls how long state F is held before the EVSE recovers (default 300 ms per IEC 61851-1:2017 Table A.5).

  </Tab>
  <Tab title="AC HLC (ISO 15118)">

    When `ac_hlc_enabled` is `true`, EvseManager coordinates with the SLAC and ISO 15118 helper modules:

    ```text
    B2 (5% PWM triggers SLAC) → SLAC matching → TLS/V2G handshake
        → ChargeParameterDiscovery → PowerDelivery → CurrentDemand → SessionStop
    ```

    Setting `ac_hlc_use_5percent` to `true` is strongly recommended because almost no production EVs will initiate SLAC on a nominal-duty PWM signal.

  </Tab>
  <Tab title="DC Charging">

    DC mode extends the AC state machine with additional cable-check and precharge phases before current flows:

    ```text
    B2 (SLAC/HLC) → CableCheck (IMD isolation test)
        → Precharge (ramp output voltage to EV battery level)
        → CurrentDemand (closed-loop current/power delivery)
        → WeldingDetection → SessionStop
    ```

    The `imd` (isolation monitor) and `powersupply_DC` requirements must be connected. The `cable_check_enable_imd_self_test` parameter ensures IEC 61851-23:2023 compliance.

  </Tab>
</Tabs>

## Energy Management Integration

EvseManager participates in EVerest's tree-based energy management by providing the `energy_grid` interface. Every update interval, it publishes an `energy_flow_request` up the tree that describes its current power needs and the limits it can accept. The EnergyManager responds by publishing `enforced_limits` back down to the EVSE, which EvseManager then enforces on the BSP (via PWM duty cycle for AC) or on the DC power supply (via current/power setpoints).

Setting `request_zero_power_in_idle` to `true` is recommended in multi-EVSE deployments so that idle EVSEs do not hold capacity that could be given to charging EVSEs.

## Error Handling

EvseManager monitors errors from all its requirements. Most errors cause the EVSE to become **inoperative** until the error is cleared. Two categories of shutdown exist:

- **Emergency Shutdown** (high-severity errors): PWM is immediately set to state F, the DC power supply is switched off, and contactors open without waiting.
- **Error Shutdown** (medium/low-severity errors): If HLC is active the error is signaled to the EV via the protocol before powering down; the DC supply and contactor are then opened.

The following errors do **not** cause the EVSE to become inoperative:
- `evse_manager/Inoperative`, `evse_manager/MREC11CableCheckFault`
- `evse_board_support/MREC3HighTemperature`, `evse_board_support/MREC18CableOverTempDerate`
- Any `VendorWarning` from BSP, connector lock, AC RCD, isolation monitor, or power supply
