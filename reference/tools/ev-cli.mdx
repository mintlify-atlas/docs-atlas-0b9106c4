The `ev-cli` command-line tool is part of the `ev-dev-tools` Python package and serves as the primary code-generation frontend for EVerest module development. It reads YAML-based interface and module manifest definitions and emits C++ header files, glue code, and CMake build files — the same generation pipeline that the EVerest CMake build system runs automatically during a full build. As a developer, you invoke `ev-cli` directly when creating a new module, regenerating headers after an interface change, or inspecting what a re-run would modify before committing.

## Installation

There are two ways to obtain `ev-cli`: activate the Python virtual environment that an EVerest build creates automatically, or install the package manually.

<Tabs>
  <Tab title="From EVerest build venv">
    Build EVerest normally. The CMake build step creates a Python venv inside your build directory and installs `ev-dev-tools` into it.

    ```bash
    cd build/
    source ./venv/bin/activate
    ev-cli --help
    ```

    This approach requires no additional package management and guarantees that the `ev-cli` version matches the interface schemas bundled with your build.
  </Tab>
  <Tab title="Manual pip install">
    Install the package directly from the EVerest monorepo on GitHub. This is useful for CI pipelines or workstations where a full EVerest build has not been run.

    ```bash
    python3 -m pip install git+https://github.com/everest/EVerest.git@main#subdirectory=applications/utils/ev-dev-tools
    ```

    The package requires Python ≥ 3.7 and depends on `jinja2 ~=3.1`, `jsonschema ~=4.26`, `stringcase ~=1.2`, and `pyyaml ~=6.0`.
  </Tab>
</Tabs>

## Subcommands

`ev-cli` is organized into four subcommands. Each subcommand also supports a short alias shown in parentheses.

<Accordion title="ev-cli module (mod) — Create and update module scaffolding">
The `module` subcommand creates or updates the auto-generated C++ file tree for an EVerest module. It reads `modules/<ModuleName>/manifest.yaml` and the interface YAML files the module depends on.

**Actions:**

| Action | Alias | Description |
|--------|-------|-------------|
| `create` | `c` | Create the initial module scaffold from `manifest.yaml`. |
| `update` | `u` | Re-generate headers and `CMakeLists.txt` after manifest or interface changes. |
| `generate-loader` | `gl` | Regenerate only the `ld-ev.hpp`/`ld-ev.cpp` loader glue files. |

**Files generated by `create`:**

- `CMakeLists.txt` — CMake build instructions for the module
- `ld-ev.hpp` / `ld-ev.cpp` — EVerest framework loader glue code
- `<ModuleName>.hpp` / `<ModuleName>.cpp` — module header and implementation stub
- `<impl-id>/<InterfaceName>Impl.hpp` / `<impl-id>/<InterfaceName>Impl.cpp` — one subdirectory per provided interface, containing the interface implementation class

**Update safety rules:**
1. `.cpp` source files are **never** overwritten by `update`. Only `create --force` resets them.
2. `.hpp` header files and `CMakeLists.txt` **are** updated when their interface dependencies change.
3. User-authored code inside UUID-delimited guard blocks is preserved through updates:

```cpp
// ev@75ac1216-19eb-4182-a85c-820f1fc2c091:v1
// Your custom code is kept here across updates
// ev@75ac1216-19eb-4182-a85c-820f1fc2c091:v1
```

**Key options for `create` and `update`:**

| Option | Description |
|--------|-------------|
| `--force` / `-f` | Force overwrite even for files that would normally be skipped. |
| `--diff` / `-d` | Dry-run: show a diff of what would change without writing any files. |
| `--only <files>` | Comma-separated list of files to touch. Pass `which` to list available targets. |

</Accordion>

<Accordion title="ev-cli interface (if) — Generate C++ headers for interfaces">
The `interface` subcommand generates `Implementation.hpp` and `Interface.hpp` C++ header pairs from interface YAML definitions located at `./interfaces/*.yaml`.

**Actions:**

| Action | Alias | Description |
|--------|-------|-------------|
| `generate-headers` | `gh` | Generate C++ headers for one or all interfaces. |
| `get-templates` | `gt` | Print the paths to the Jinja2 template files used for generation. |

For each interface, two header files are generated in `./build/generated/include/generated/interfaces/<InterfaceName>/`:

- `Implementation.hpp` — the **implementer's** view; provides the abstract base class a module inherits when it offers this interface
- `Interface.hpp` — the **user's** view; provides the proxy class a module uses when it requires this interface

The build system calls this action automatically during a normal `cmake --build`. You invoke it manually after editing an interface YAML to preview the output or force an immediate regeneration.

</Accordion>

<Accordion title="ev-cli types (ty) — Generate C++ headers for types">
The `types` subcommand generates C++ header files from the YAML type definitions in `./types/**/*.yaml`. Type headers are placed in `./build/generated/generated/types/`.

**Actions:**

| Action | Alias | Description |
|--------|-------|-------------|
| `generate-headers` | `gh` | Generate type headers for one or all type namespaces. |
| `get-templates` | `gt` | Print the path to the `types.hpp.j2` Jinja2 template. |

Type generation runs automatically as part of a full build and also as a prerequisite step inside `interface generate-headers` and `module update`.

</Accordion>

<Accordion title="ev-cli helpers (hlp) — Utility commands">
The `helpers` subcommand provides small utilities useful during EVerest development.

| Action | Description |
|--------|-------------|
| `generate-uuids <count>` | Generate `<count>` RFC 4122 version-4 UUIDs, one per line. Useful for populating the `ev@<uuid>:v1` guard blocks in module headers. |
| `yaml2json <input> <output>` | Convert a YAML file to JSON. |
| `json2yaml <input> <output>` | Convert a JSON file to YAML. |

</Accordion>

## Common Options

The `module`, `interface`, and `types` subcommands all accept the following options in addition to their action-specific flags.

<ParamField path="--work-dir" type="string" default=".">
  Working directory that contains the `modules/` tree and manifest definitions.
</ParamField>

<ParamField path="--everest-dir" type="string (space-separated list)" default="auto-detected from install and ../EVerest">
  One or more root directories of EVerest core, or any directory containing `interfaces/` and `types/` subdirectories. Pass multiple paths as space-separated values to merge definitions from several directories. Short alias: `-ed`.
</ParamField>

<ParamField path="--schemas-dir" type="string" default="../everest-framework/schemas">
  Directory containing the EVerest framework JSON schema files used to validate manifest and interface definitions. Defaults to the path discovered inside the build directory's `CMakeCache.txt` when the default does not exist.
</ParamField>

<ParamField path="--clang-format-file" type="string" default=".">
  Path to the directory containing a `.clang-format` file. When present, generated C++ output is formatted before writing.
</ParamField>

<ParamField path="--disable-clang-format" type="flag">
  Skip `clang-format` post-processing on generated files.
</ParamField>

<ParamField path="--build-dir" type="string" default="./build">
  EVerest build directory. Used to auto-discover the schemas directory from `CMakeCache.txt` when `--schemas-dir` is not specified. Short alias: `-bd`.
</ParamField>

<ParamField path="--everest-projects" type="string (space-separated list)" default="EVerest">
  EVerest project names used for automatic directory detection. Enables `ev-cli` to locate the `interfaces/` and `types/` trees of named projects relative to the build directory. Short alias: `-ep`.
</ParamField>

<ParamField path="--licenses" type="string" default="../licenses">
  Directory from which `ev-cli` attempts to parse custom license header texts. License headers are embedded in every generated file. The built-in Apache-2.0 header is always available; point this at a directory with additional `.txt` files to support other licenses referenced in `manifest.yaml`. Short alias: `-lc`.
</ParamField>

## Examples

### Create a new module

The following assumes you have a `modules/Example/manifest.yaml` describing a module named `Example` that provides a single implementation `main` backed by `SampleInterface`.

```yaml
description: Example module
metadata:
  license: https://opensource.org/licenses/Apache-2.0
provides:
  main:
    description: SampleInterface implementation
    interface: SampleInterface
```

Run the scaffold generator from the repository root:

```bash
ev-cli module create Example
```

This writes the following files into `modules/Example/`:

```text
modules/Example/
├── CMakeLists.txt
├── ld-ev.hpp
├── ld-ev.cpp
├── Example.hpp
├── Example.cpp
└── main/
    ├── SampleInterfaceImpl.hpp
    └── SampleInterfaceImpl.cpp
```

<Note>
The `Example.cpp` and `main/SampleInterfaceImpl.cpp` files contain only empty stubs. Implement your logic there — `ev-cli update` will never overwrite `.cpp` files.
</Note>

### Regenerate headers after an interface change

After modifying `interfaces/SampleInterface.yaml`, update the generated headers for the `Example` module without touching any `.cpp` source files:

```bash
ev-cli module update Example
```

To preview the diff before writing:

```bash
ev-cli module update Example --diff
```

To regenerate all C++ headers for every interface at once (as the build system does):

```bash
ev-cli interface generate-headers
```

To regenerate only the `SampleInterface` headers:

```bash
ev-cli interface generate-headers SampleInterface
```

### Selective file regeneration with `--only`

Query which files a `create` run would touch for the `Example` module:

```bash
ev-cli module create Example --only which
```

```text
Available files for category "core"
  cmakelists
  ld-ev.hpp
  ld-ev.cpp
  module.hpp
  module.cpp
Available files for category "interfaces"
  main.hpp
  main.cpp
```

Force-recreate only `CMakeLists.txt` and the interface implementation source file:

```bash
ev-cli module create Example --only main.cpp,cmakelists --force
```

Update only the module header, leaving all other files untouched:

```bash
ev-cli module update Example --only module.hpp
```

<Warning>
Generated files are never automatically deleted. If you rename or remove an interface ID from `manifest.yaml`, manually remove the corresponding subdirectory under `modules/<ModuleName>/` to keep the source tree consistent.
</Warning>
