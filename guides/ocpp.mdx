EVerest consolidates all OCPP support into a single module called **OCPPmulti**, which implements OCPP 1.6J, 2.0.1, and 2.1. A single `Mode` configuration parameter selects the protocol generation at runtime, so the same EVerest configuration file can serve charging stations that connect to 1.6 or 2.x Charge Station Management Systems (CSMSs). OCPPmulti is the recommended path for all new integrations — the older per-version OCPP and OCPP201 modules are deprecated.

## Quick Start: Run the SIL Example

The EVerest repository ships a ready-to-use Software-in-the-Loop configuration for OCPPmulti. Start it with:

```bash
${EVEREST_WORKSPACE:?}/EVerest/build/run-scripts/run-sil-ocpp-multi.sh
```

OCPP message logs are written to `/tmp/everest_ocpp_logs/` in multiple formats on every start.

## Choosing the OCPP Version

The `Mode` configuration parameter of the OCPPmulti module selects the protocol generation:

| Value | Behaviour |
|---|---|
| `Only1.6` | Use OCPP 1.6J only |
| `Only2` | Use OCPP 2.x (default) |
| `Prefer1.6` | Reserved — currently equivalent to `Only1.6` |
| `Prefer2` | Reserved — currently equivalent to `Only2` |

Within OCPP 2.x, the concrete version (2.0.1 or 2.1) is negotiated with the CSMS during the initial WebSocket handshake. The `SupportedOcppVersions` variable in the `InternalCtrlr` device-model component controls which 2.x versions the charging station offers. Configure it as a comma-separated list (`ocpp2.1,ocpp2.0.1`) in the `InternalCtrlr` component config file.

<Note>
  Which 2.x version is actually used depends on what the CSMS accepts. Both `ocpp2.1` and `ocpp2.0.1` are offered by default.
</Note>

## Device Model Configuration

OCPPmulti is configured entirely through the OCPP device model, regardless of protocol version. The device model is defined and populated from JSON files — one per Component. Each Component file defines Variables, their VariableCharacteristics, VariableAttributes, and optional VariableMonitoring entries.

Set the `DeviceModelConfigPath` module parameter to the directory containing two subdirectories:

- **`standardized/`** — OCPP-standardised components (rarely need modification)
- **`custom/`** — charging-station-specific components

The [device model definitions bundled with libocpp](https://github.com/EVerest/EVerest/tree/main/lib/everest/ocpp/config/common/component_config) are the recommended starting point. They ship as an example configuration for two EVSEs.

**Example: `LocalAuthListCtrlr` component config**

```json
{
  "description": "Schema for LocalAuthListCtrlr",
  "name": "LocalAuthListCtrlr",
  "type": "object",
  "properties": {
    "LocalAuthListCtrlrEnabled": {
      "variable_name": "Enabled",
      "characteristics": {
        "supportsMonitoring": true,
        "dataType": "boolean"
      },
      "attributes": [
        {
          "type": "Actual",
          "mutability": "ReadWrite",
          "value": true
        }
      ],
      "description": "If this variable exists and reports true, Local Authorization List is enabled.",
      "default": true,
      "type": "boolean"
    },
    "BytesPerMessageSendLocalList": {
      "variable_name": "BytesPerMessage",
      "characteristics": {
        "supportsMonitoring": true,
        "dataType": "integer"
      },
      "attributes": [
        {
          "type": "Actual",
          "mutability": "ReadOnly",
          "value": 4096
        }
      ],
      "description": "Maximum number of bytes in a SendLocalList message.",
      "type": "integer"
    }
  },
  "required": ["BytesPerMessageSendLocalList"]
}
```

The config files are parsed at startup to initialise an SQLite database. Values already modified at runtime by the CSMS are protected — editing a JSON file after first boot has no effect on those variables.

## Network Configuration and CSMS Connectivity

OCPPmulti uses **NetworkConfiguration** component instances (slots) to define how the charging station connects to a CSMS. This applies to both OCPP 1.6 and 2.x.

Modify the following variables in `standardized/NetworkConfiguration_1.json` to point to your CSMS:

| Variable | Description |
|---|---|
| `OcppCsmsUrl` | WebSocket endpoint of the CSMS, without the station identifier (e.g. `wss://csms.example.com:443`) |
| `SecurityProfile` | `0` = no security, `1` = Basic Auth over `ws://`, `2` = TLS + server cert, `3` = mutual TLS |
| `OcppInterface` | Network interface: `Wired0`, `Wireless0`, or `Any` |
| `OcppTransport` | Transport encoding — use `JSON` |
| `MessageTimeout` | Message timeout in seconds (minimum 1) |

The charging station identity and credentials fall back to `SecurityCtrlr.Identity` and `SecurityCtrlr.BasicAuthPassword` unless overridden per-slot.

The `NetworkConfigurationPriority` variable in `OCPPCommCtrlr` controls failover order as a comma-separated list of slot numbers (e.g. `"1,2"`). The shipped configuration uses only slot 1 and keeps slot 2 as a writable spare.

<Warning>
  For SecurityProfile 2 or 3 (TLS), you must provision the required certificates and private keys via the EvseSecurity module before OCPPmulti can establish a secure connection.
</Warning>

### Adding Network Configuration Slots

To define a second or third connection profile:

<Steps>
  <Step title="Copy an existing slot file">
    Copy `NetworkConfiguration_1.json` to `NetworkConfiguration_3.json` (use any slot number).
  </Step>
  <Step title="Update the instance field">
    ```json
    {
      "name": "NetworkConfiguration",
      "instance": "3",
      ...
    }
    ```
  </Step>
  <Step title="Set all mandatory variables">
    Set `OcppCsmsUrl`, `SecurityProfile`, `OcppInterface`, `OcppTransport`, and `MessageTimeout`. Missing any of these causes the slot to be silently skipped during failover.
  </Step>
  <Step title="Add to the priority list">
    In `OCPPCommCtrlr.json`, update `NetworkConfigurationPriority` (e.g. change `"1"` to `"1,3"`) and append the slot number to the variable's `valuesList`.
  </Step>
</Steps>

## OCPP 1.6 Legacy Config Migration

For existing OCPP 1.6 deployments, OCPPmulti provides a one-time migration path from the legacy JSON key-value config into the device model database.

**Pure device model (recommended for new deployments):** Configure everything via component JSON files. OCPPmulti maps OCPP 1.6 configuration keys to device model variables automatically using built-in mappings documented in `lib/everest/ocpp/config/v16_to_v2_mapping.md`.

**Legacy JSON migration (for existing deployments):** Set `EnableLegacyConfigMigration: true` in the OCPPmulti module config. On first startup, when the device model database does not yet exist, the legacy JSON file referenced by `ChargePointConfigPath` is migrated once. Network connection details (`CentralSystemURI`, `SecurityProfile`, `AuthorizationKey`) are written to the `NetworkConfiguration` slot given by `Ocpp16NetworkConfigSlot`. Once the database exists, the migration is skipped and the legacy JSON is never read again.

## Enabling Plug & Charge

To enable Plug&Charge via OCPPmulti, configure the following OCPP variables in your component config files:

| Key | OCPP Version | Purpose |
|---|---|---|
| `ISO15118PnCEnabled` | 1.6 + 2.x | Enable contract certificate authorization |
| `ISO15118CertificateManagementEnabled` | 1.6 only | Enable DataTransfer-based cert management |
| `CentralContractValidationAllowed` | 1.6 + 2.x | Allow CSMS to validate contracts when local validation fails |
| `ContractValidationOffline` | 1.6 + 2.x | Allow offline validation via auth cache |
| `ISO15118Ctrlr::V2GCertificateInstallationEnabled` | 2.x only | Allow CSMS to install SECC leaf certificates |
| `ISO15118Ctrlr::ContractCertificateInstallationEnabled` | 2.x only | Allow contract certificate installation in the EV |

See the [Plug & Charge guide](/guides/plug-and-charge) for the full EVerest module configuration required alongside these OCPP parameters.
